# v0.1 readiness — promotion evidence, dogfooding and scale validation

The v0.1 question this pass answers: can `phlo-transform` be used repeatedly
on real projects — across machines and CI stages, against real
Trino/Iceberg infrastructure — rather than merely passing unit tests?
This document records what was built, what was measured, and what is still
known-unfinished.

## Portable promotion evidence

Promotion evidence is persisted in the state store (SQLite or Postgres) as
append-only `EvidenceRecord`s and treated as the authority; the JSON files
under `.phlo/transform/` are exports and debugging output, not the source of
truth. Records bind exactly to candidate/target references *and* their commit
hashes, and stale, missing, corrupt or divergent evidence fails closed.

Semantics established here and covered by engine tests:

- **Store-first reads.** When a store is configured, records win over files;
  a store read failure is an error, not a cache miss, so a workspace never
  silently audits stale local files because Postgres was unreachable.
- **Legacy import.** Workspaces written before the evidence table existed
  keep working: artifact-only evidence is imported into the store on first
  read and becomes portable from then on.
- **Write ordering.** The store record is written *before* the artifact
  files, so a failed record write cannot leave a newer file permanently
  masked by an older record (a review finding: store-first reads never
  consult files once any record exists).
- **Dedup.** Re-provisioning an unchanged binding does not append a new
  record — only a changed binding does. Environment evidence no longer
  grows on every identical `run --ref`.
- **Idempotent cleanup.** `ref delete` and `promote --cleanup` treat an
  already-deleted branch as success and still remove orphaned evidence, so
  a cleanup that died between branch deletion and evidence removal
  completes on retry instead of wedging.
- **Shared path.** CLI and daemon evaluate promotion through the same
  `evaluate_promotion`/`persist_branch_diff`/`cleanup_candidate` code —
  evidence written by a `phlo-transform run` in CI audits a `promote` issued
  from a laptop, and vice versa.

## A real bug dogfooding found: composite `@key`

`@key a,b` used to generate per-column `unique a` and `unique b` tests —
asserting each column is *individually* unique, which is not what a
composite key means (the pair is unique; its members need not be). It now
generates `not_null` per column plus one composite `unique(a, b)`. Locked in
by `a_composite_key_asserts_one_composite_unique` in
`crates/phlo-transform-core/tests/analysis.rs`; documented in
`docs/semantic.md`.

## Two more bugs the live run found: source qualification and catalog cleanup

**Source qualification.** The rewriter used to leave external source
references untouched, so `from external.feed` compiled to a two-part name
that resolved through the warehouse's *session* catalog — while the engine's
seed loads and source probes already targeted the environment's catalog via
`relation_for_source`. Under a Nessie candidate that read the base branch
(or failed outright with `MISSING_CATALOG_NAME`) while writes went to the
candidate. The rewriter now emits `relation_for_source` for any source with
fewer than three parts when a default catalog is configured — compiled SQL
and the engine's physical mapping finally agree, and a candidate reads and
writes on its own branch. Explicitly catalog-qualified sources still pass
through, as do all source names when no catalog is configured. Locked in by
`a_candidate_compile_qualifies_source_references` in
`crates/phlo-transform-engine/tests/engine.rs` plus the updated
`compiled_sql_rewrites_models_and_preserves_sources` in
`crates/phlo-transform-core/tests/compilation.rs`; documented in
`docs/engine.md` and `docs/wap.md`.

**Catalog cleanup.** `ref delete` deleted the branch and removed evidence
but never dropped the candidate catalog — every ref deleted through the CLI
leaked a Trino catalog. It now routes through `cleanup_candidate` (the same
path `promote --cleanup` uses), so a catalog evidence proves Phlo
provisioned is dropped, and an unproven one is left in place and reported.
Verified live: the dogfood script's final `ref delete` removes both the
branch and its `phlo_ci_dogfood_*` catalog.

**Seed loading.** The Trino adapter implemented no `load_csv`, so any
project with seeds could not run on Trino at all — seeds reported
unsupported and every dependent model blocked. It now parses CSVs (RFC
4180 via the `csv` crate), infers column types, preserves VARCHAR
whitespace verbatim, escapes literals correctly and batches inserts.

## Dogfooding workspace

`scripts/dogfood_workspace.py` generates a realistic 120-model workspace and
`scripts/dogfood.sh` drives the full lifecycle against it:

```bash
bash scripts/dogfood.sh /tmp/dogfood        # generates + runs all checks
```

The generated workspace has 5 namespaces, 7 seeds, table and view models,
incremental append and keyed-merge models, contracts, `@key`/`@not-null`
directives (40 tests total), multi-hop dependencies, and a failure lab whose
seed toggles a model between pass and fail.

The script verifies, in order: `check` → `list` → cold `run` (all 120 build)
→ warm `run` (all 120 skip — recorded output identities verified) → `test`
→ `lineage`/`impact` → a file edit + `plan --since` (exactly the touched
model plus its dependents are selected) → deliberate failure →
`--retry-failed` (only the failed subset reruns) → `--resume` on a finished
run (refused, with guidance pointing at `--retry-failed`) → `state`
inspection. When `PHLO_NESSIE_ENDPOINT`/`PHLO_TRINO_ENDPOINT` are set it
additionally exercises the full branch lifecycle against live
infrastructure: provision a production `phlo_main` catalog and run the
workspace on `main` (this gives the Nessie repository a real commit
history — a candidate cut from the no-ancestor sentinel can never satisfy
the merge gate), then `ref create` a unique timestamped candidate, `run
--ref` against it with `--retries`, branch `diff`, `promote --check` and
`ref delete` (which drops the owned candidate catalog).

Nessie Iceberg catalogs cannot store views, so the script rewrites the
generated workspace's view materialisations to tables for the live leg —
the DuckDB leg still exercises views. Seed loading on Trino is real: the
adapter parses CSVs (header handling, type inference, batched inserts) and
writes them into the environment's catalog.

Latest run: **23/23 checks pass** — the 16 DuckDB checks plus the seven
live Nessie/Trino steps above.

## Planning benchmark against real Trino + Iceberg

`crates/phlo-transform-trino/tests/plan_scaling_e2e.rs` starts Nessie +
Trino (testcontainers, Iceberg catalog on a `main` branch), materialises a
generated layered workspace, and times planning while counting every
adapter call:

```bash
cargo test -p phlo-transform-trino --test plan_scaling_e2e -- \
  --ignored --nocapture
# PHLO_BENCH_MODELS="100,1000,5000"  PHLO_BENCH_CHANGED=1
```

Scenarios per size: **cold** (no state, no tables), **materialise** (the
`Runner::apply` that creates the tables — prerequisite, not a planning
measurement), **warm** (every model recorded with a live output identity —
the steady-state `plan`), **changed-subset** (1% of models edited, full
selection), and **since** (the `changed` selector path `--since` resolves
to, driven by the recorded-state change set). The report prints wall time,
per-method adapter call counts and cumulative call latency.

Environment: Apple M2 Pro / 32 GB, OrbStack Docker 29.4.0, `trinodb/trino`
+ `ghcr.io/projectnessie/nessie` on a private Docker network, warehouse on
the container filesystem. During a 1,000-model materialise Trino peaked at
~530% CPU / ~6.8 GB — the coordinator is the bottleneck, not the client.

### The dominant finding: per-relation snapshot reads

Existence probing is already batched — a cold plan over 5,000 models is a
**single** `information_schema` query. The warm plan is not: every model
recorded with a strong `output_identity` pays one live `SELECT … FROM
"table$snapshots"` drift check (`buffered(16)` in the planner). Measured:
1.4s at 100 models, 9.2s at 1,000, 29.6s at 5,000 — roughly 6ms/model of
wall time, since ~15 of 16 parallel slots stay busy (per-call latency rises
to ~87–134ms under concurrency versus ~16–29ms serial, so the speedup is
real but not free). The `--since` path dodges it almost entirely — only the
change set's models are probed (0.6s at 5,000).

Two warm-plan models out of 5,000 rebuilt instead of skipping — consistent
with a snapshot read landing between a table's Nessie commit and its
visibility to the next reader. That is the drift check *doing its job*
(rebuild on any unproven identity), and the cost of honesty is one extra
build, not stale output.

This is the correct-by-construction cost: the drift check is what makes a
recorded version hash *evidence* rather than a guess — skipping it would let
a table silently rewritten outside phlo pass as unchanged. A safe speedup
would be one batched snapshot read per schema (Trino cannot list snapshots
across tables in one query, so this means `system` tables or a Nessie-side
API, neither of which exists today), or a documented opt-out for callers
who accept drift risk. Neither is in v0.1.

### Transient-failure hardening that fell out of this

At 1,000 tables the materialise hit `GENERIC_INTERNAL_ERROR: Failed to
execute POST request against …/trees/main/contents` — a Nessie REST client
failure the Iceberg connector wraps as an internal error. Trino statement
errors were *never* marked retryable, so one transient commit failure
failed the whole run. Now `EXTERNAL` and `INSUFFICIENT_RESOURCES` error
types, and the Nessie-client signature wrapped in `GENERIC_INTERNAL_ERROR`,
are classified retryable and the runner's `RetryPolicy` applies
(`--retries`). Covered by unit tests in `phlo-transform-trino`.

## Known gaps for v0.1

- **Warm-plan scale.** The snapshot-read drift check is O(models); see the
  finding above. Documented behaviour, not a regression — but the first
  thing to attack if v0.1 must plan fast at 5k+.
- **No TLS/auth on the Postgres state client** (`NoTls`) — fine for local
  and trusted-network CI; document or extend before shared-CI over
  untrusted networks.
- **Nessie Iceberg catalogs cannot store views** — a platform limitation,
  not a phlo bug; projects targeting a Nessie-backed catalog must
  materialise as tables (the dogfood script rewrites view materialisations
  for its live leg).
- **A Nessie repository needs a real `main` head before promotion.** A
  candidate cut while `main` still sits at the no-ancestor sentinel can
  never satisfy the merge gate; run the workspace on `main` (e.g.
  `run --catalog phlo_main`) before branching, as the dogfood script does.
- **The ignored e2e tests** remain `--ignored` (Docker-gated); they all
  pass but run on demand/in CI, not in `cargo test`.
