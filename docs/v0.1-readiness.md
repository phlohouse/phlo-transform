# v0.1 release-candidate readiness

The question this report answers: can `phlo-transform` be called a v0.1
release candidate based on what it actually does on real infrastructure —
not on architecture or unit tests alone.

## Executive verdict

**Ready for v0.1 RC.**

Every acceptance gate below is met against live Trino/Iceberg/Nessie
infrastructure, a real Postgres state store, and a 120-model dogfood
workspace exercised end to end — including the last piece that was
classification-only: `cached` now has real execution semantics (verified
adoption, not just a label). The known limitations are documented, bounded,
and fail closed rather than silently wrong.

## What was validated

- **Workspace suite.** `cargo test --workspace` — all unit and integration
  tests pass (engine 173, CLI 79 incl. golden-path snapshots, core,
  daemon API, nessie client, dbt importer).
- **Real Trino + Iceberg + Nessie e2e** (testcontainers, Docker): the
  existing WAP promotion flow plus a new candidate cache-reuse test that
  proves a candidate branch adopts inherited materialisations with zero
  model SQL, preserves source run/timestamp provenance, and falls back to
  a real build when a table is externally rewritten.
- **Dogfood script** (`scripts/dogfood.sh`, 120-model generated
  workspace): 24/24 checks — `check`, `list`, cold/warm runs, tests,
  lineage/impact, `plan --since`, deliberate failure, `--retry-failed`,
  `--resume` refusal on a finished run, state inspection — plus the live
  leg: `run` on `main`, `ref create`, `run --ref` that asserts every model
  result is `cached` (JSON-checked, not just exit code), `diff`,
  `promote --check`, `ref delete` with catalog cleanup.
- **Real planning benchmark** at 100 / 1,000 / 5,000 models including
  candidate cache-reuse and forced-miss tiers (numbers below).
- **Postgres state store** against real Postgres 16 — 5/5 tests.
- **Daemon** environment isolation (candidate run cannot touch base
  tables) and bearer-auth gating (401 without token on every endpoint
  except `/status`).
- **Install/upgrade**: `cargo install --path` produces a working binary;
  `init`/`check`/`run --adapter duckdb` pass on a clean workspace; a
  pre-evidence SQLite `state.db` opens, migrates (missing tables created,
  missing columns added), and serves reads without manual surgery; a
  Postgres URL's credentials do not appear in connect errors.
- **Other ignored e2e**: `golden_path`, `trino_e2e` ×3 (run+test, keyed
  diff, partitioned diff), `trino_incremental_e2e` (MERGE on Iceberg),
  `nessie_wap_e2e`, daemon `nessie_e2e` — all pass.

## Correctness findings

Bugs found by actual use, each locked in by a regression test:

- **`Cached` was classification-only.** The planner could say a model was
  reusable but the runner never wrote a target-environment record, so the
  adoption was neither durable nor honest. Now a verified adoption
  persists an environment-local `MaterializedRecord` claiming the source
  run id and timestamp verbatim. Tests: `a_cached_run_adopts_the_verified_output_into_the_environment`,
  `a_cached_run_falls_back_to_build_when_identity_drifts`,
  `a_cached_run_adopts_the_source_environments_watermark` (engine tests);
  `candidate_reuses_inherited_materialisations_without_rebuilding`
  (Trino/Nessie e2e).
- **Model versions were not portable across environments.** The version
  target input included the catalog, so a Nessie candidate compiling
  against its own catalog produced different hashes and could never match
  a base record. The catalog is an environment binding, not model content:
  the target input is now `schema.table|materialization` and
  `COMPILER_SEMANTICS_VERSION` is 3. Retarget detection survives through
  full target-display comparison (`changed_models` treats a moved target
  as changed; the planner emits `target_change`). Tests:
  `cache_reuse_matches_across_catalogs_on_the_same_content_slot`,
  `cache_reuse_rejects_a_different_content_slot`,
  `a_catalog_retarget_adopts_the_visible_output`,
  `a_catalog_retarget_without_verifiable_identity_rebuilds`.
- **Composite `@key a,b` generated per-column unique tests** instead of
  one `unique(a, b)`. Now `not_null` per column plus a composite unique.
  Test: `a_composite_key_asserts_one_composite_unique`.
- **Source references bypassed the environment catalog** — a candidate
  read the base branch (or failed) while writing the candidate. The
  rewriter now emits `relation_for_source` for unqualified sources under a
  default catalog. Tests: `a_candidate_compile_qualifies_source_references`,
  `compiled_sql_rewrites_models_and_preserves_sources`.
- **`ref delete` leaked the provisioned Trino catalog.** It now routes
  through `cleanup_candidate`; a Phlo-provisioned catalog is dropped, an
  unproven one is left and reported. Verified live in the dogfood script.
- **Trino had no `load_csv`** — any project with seeds could not run on
  Trino. Implemented with RFC 4180 parsing, type inference, batched
  inserts.
- **Transient identity reads masqueraded as "no verifiable output".**
  `iceberg_snapshot` swallowed every error as `None`, so a Nessie/Trino
  blip demoted an unchanged model to a rebuild — observed at scale in the
  benchmark (a 1,000-model candidate run that adopted 999 and rebuilt 1,
  and earlier 2-of-5,000 warm-plan misses). Non-missing-relation errors
  now retry (150ms, 400ms) before reporting `None`; a real missing
  relation still answers immediately, and anything still unreadable fails
  closed to a build.
- **Nessie commit hiccups were never retryable.** `EXTERNAL`,
  `INSUFFICIENT_RESOURCES` and the Nessie-client signature inside
  `GENERIC_INTERNAL_ERROR` are now classified retryable so the runner's
  `RetryPolicy` applies. Covered by `phlo-transform-trino` unit tests.

## Cache reuse

`skip` and `cached` now have distinct, user-legible meanings:

- **`skip`** — this environment's own record vouches for the desired
  version *at this target*, and the live identity check confirms the
  relation still holds the recorded output.
- **`cached`** — no record in *this* environment fully vouches, but a
  matching record elsewhere does, and this environment's target provably
  already holds the same physical output. Execution adopts it: no model
  SQL runs.
- **`build`** — nothing vouches; the model executes.

Cross-environment reuse (the Nessie case) requires all of: identical
desired version hash; same content slot `schema.table` (catalogs may
differ — that is exactly branch inheritance); same adapter; a non-empty
strong `output_identity` (Iceberg snapshot id) recorded on the source;
and a live `output_identity` read through *this* environment's binding
matching it at plan time and again at run time. Records from adapters that
cannot prove physical identity (DuckDB, non-Iceberg Trino) never authorise
reuse; legacy records without adapter or identity are inert.

Run output explains itself — a cached model prints `adopted the output
recorded in <env> — snapshot:<id> verified live`; a stale-evidence
fallback prints `cache evidence stale at run time: <target> now reports
…; building instead`.

Same-environment reuse covers the retarget case: a same-version record
whose target display moved adopts the verified output into an updated
record rather than rebuilding.

**Known limitations.** Adoption requires the physical relation to already
be visible through the target environment's binding — true for Nessie
branch inheritance, not for a candidate pointed at an isolated warehouse
(it builds, correctly). There is no cross-*adapter* or cross-*engine*
reuse by design. A `plan --ref` against a never-provisioned candidate is a
read-only preview of an empty target; the CLI now prints a note saying a
`run --ref` provisions first and may adopt.

## Performance

Real Trino + Nessie + Iceberg (testcontainers on OrbStack, Apple M2 Pro).
Per-model `output_identity` snapshot reads dominate warm plans and are the
cost of honesty — the drift check is what makes a recorded version
*evidence*.

| Models | cold plan | materialise | warm plan | changed-subset | `--since` | candidate plan | candidate run | candidate miss (plan / run) |
|---|---|---|---|---|---|---|---|---|
| 100 | 1.2s / 1 call | 10.0s | 1.1s / 101 | 1.1s / 102 | 0.13s / 7 | 1.2s / 101 — 100% cached | 0.9s — 100 cached, 0 built | 1.3s / 1.6s — 95 cached + 5 built |
| 1,000 | 0.6s / 1 call | 132s | 13.8s / 1,001 | 13.5s / 1,002 | 0.4s / 12 | 13.1s / 1,001 — 100% cached | 12.6s — 1,000 cached, 0 built | 13.0s / 13.3s — 990 cached + 10 built |
| 5,000 | 1.8s / 2 calls | 291s | 27.7s / 5,001 | 56.6s / 5,002 | 1.2s / 52 | 80.7s / 5,001 — 100% cached | 57.5s — 5,000 cached, 0 built | 57.9s / 79.2s — 4,950 cached + 50 built |

(Adapter calls counted on the wrapping `CountingAdapter`; "materialise" is
the run that creates the tables, a prerequisite not a planning measure.
Candidate run = zero model SQL; its adapter calls are the identity
verification reads plus schema provisioning.)

The honest finding stands: a warm 5k plan is ~28s because 5,000 snapshot
reads run `buffered(16)` against a single small Nessie/Trino pair. The
`--since` path stays sub-second because it only probes the change set.
Candidate adoption is the same shape as a warm plan — the adoption itself
is free; the verification reads are the cost.

## UX

Improved this pass:

- `run` prints cached-adoption reasons per model; the `skip`/`cached`/
  `build` distinction is documented in SPEC §39 and `docs/engine.md`.
- `plan --ref`/`test --ref` on a never-provisioned candidate prints a
  note explaining the preview sees an empty target and that `run --ref`
  provisions + may adopt — previously it silently reported every model
  `missing_relation`.
- `compiler semantics changed` is an explicit reason when a pre-v3 record
  meets a v3 workspace (the one-time rebuild wave on upgrade explains
  itself).
- The dogfood's candidate run is asserted `cached` in JSON, not just
  exit-code green.

Still awkward (accepted for v0.1): the unprovisioned-candidate preview
cannot show adoption without provisioning (the note is the mitigation);
`--since` depends on a git checkout; the daemon and CLI surface the same
concepts but daemon responses remain more terse.

## Upgrade/migration

- **SQLite state**: additive-only migrations (`CREATE TABLE IF NOT
  EXISTS`, idempotent `ALTER TABLE ADD COLUMN`, legacy `effective_key`
  backfill). Verified by opening a hand-built pre-evidence database — all
  missing tables/columns appear and legacy rows read correctly. No manual
  surgery.
- **Postgres state**: same additive schema approach; no TLS on the client
  (`NoTls`) — documented for trusted networks.
- **Compiler semantics v2 → v3**: old records hash-miss once and rebuild
  with an explicit `compiler_semantics_change` reason. Legacy records
  lacking `adapter`/`output_identity` can never authorise cache reuse —
  fail closed by construction.
- **Promotion records**: `evidence` (branch-diff / lineage-diff /
  environment ids) is optional via serde defaults — records written before
  evidence tracking deserialize with `None`; `promotions.record_json`
  schema is unchanged.
- **Artifacts**: `plan.json`/`run.json`/`manifest.json` schemas are
  additive; `Cached` results carry `output_identity` and reasons.

## Remaining work

**Release blocker** — none known.

**Post-v0.1** (documented limitations, real but not blocking):

- Warm-plan cost is O(models × snapshot read): ~28s at 5,000. First thing
  to attack if large workspaces need fast no-op plans — needs a batched
  identity read Trino/Nessie cannot serve today, or a documented opt-out
  for callers accepting drift risk.
- Postgres state client has no TLS (`NoTls`) — trusted networks only.
- Nessie Iceberg catalogs cannot store views — platform limitation;
  Nessie-targeted projects must materialise views as tables.
- Promotion evidence ids are captured from the store post-evaluation; a
  same-timestamp evidence collision could theoretically misname which of
  two identical-kind records was consulted (ordering is
  `created_at, seq` — the window is narrow).

**Future capability** (deliberately out of scope): a generic distributed
cache abstraction (this pass solves the Phlo/Iceberg/Nessie case only);
cross-adapter reuse; batched snapshot reads.

## Top five priorities after v0.1

From observed use, not roadmap speculation:

1. **Batched/alternative output-identity reads** — the 28s warm plan at
   5k is the single largest recurring cost; every candidate run pays it
   too.
2. **Postgres TLS support** — the only thing standing between "local/trusted
   network" and "shared CI over untrusted networks" deployments.
3. **Provisioned-candidate `plan` parity** — a `plan --ref` that can show
   adoption without a preceding `run` would remove the most confusing
   output a new user sees.
4. **`state`/`state evidence` ergonomics** — evidence ids on promotion
   records are now queryable; making the join obvious in human output
   (`promotion → evidence id → payload`) closes the audit loop for
   non-JSON readers.
5. **Transient-resilience budget review** — identity-read retries fixed
   the observed flake; at 10k+ models, watch whether 150/400ms retry
   delays suffice or the concurrency window needs tuning.
